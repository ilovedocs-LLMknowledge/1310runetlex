# ТЗ: вкладка «Итоговая редакция» и история прогонов

Версия 1.0 · 14.10.2026

## 1. Цель

Решить обратную задачу к уже существующей вкладке «Протокол разногласий». Программа получает исходный договор и документы, которые его меняют, и собирает договор в итоговой редакции. Каждое изменение в нём видно как правка Word (режим рецензирования), а автор правки — документ, из которого она пришла.

Дополнительно программа ведёт историю всех прогонов обеих вкладок и позволяет открыть папку с файлами любого прогона.

## 2. Входы

| Вход | Формат | Обязательность |
|---|---|---|
| Исходный договор | .docx | обязателен, ровно один |
| Протокол разногласий | .docx с таблицей «пункт / редакция / редакция [/ согласованная]» или скан (PDF, JPG, PNG) | 0..N |
| Дополнительное соглашение | .docx (свободный текст) или скан (PDF, JPG, PNG) | 0..N |

Всего нужен хотя бы один изменяющий документ.

У каждого изменяющего документа (далее — **источник**) есть:
- вид (протокол / ДС);
- номер и дата, которые определяются автоматически и редактируются вручную;
- порядок применения (по умолчанию — по дате, вручную можно переставить);
- автор правок: строка, которую видно в Word, например «Протокол разногласий от 01.02.2026» или «ДС № 2 от 15.03.2026».

## 3. Выход

1. **Итоговая редакция в .docx.** Это исходный договор, к которому все включённые правки применены как `w:ins` / `w:del`:
   - формат, стили и автонумерация исходника сохраняются;
   - правки каждого источника подписаны своим автором, поэтому в Word их можно принимать и отклонять по источникам;
   - если принять все правки, получится договор в итоговой редакции.
2. **Отчёт о сборке** (показывается на экране и сохраняется в архив как `отчёт.md`):
   - сколько правок применено, а сколько пропущено (по каждому источнику);
   - правки, которые не удалось сопоставить с договором;
   - предупреждения: текстовая нумерация не сдвинулась, есть перекрёстные ссылки на сместившиеся пункты, договор уже содержал правки.
3. **Запись в истории** и папка в `Архив/` (раздел 9).

Имя файла: `<имя договора> — итоговая редакция.docx`.

## 4. Модель правки

Источник любого вида (протокол docx, скан, ДС) превращается в список правок одного формата:

```
{
  id, source_id, source_label, seq,
  action,        // см. ниже
  target,        // номер пункта, как в документе: "5.3", "5.3.1", "7"
  targets,       // все старые номера, если пункт объединяет несколько: ["6.16.2", "6.16.3"]
  anchor,        // для insert: после какого пункта вставить (необязательно)
  sub_target,    // уточнение: "абз. 2", "пп. б" (необязательно)
  old_text,      // текст пункта/слов до изменения (если известен)
  new_text,      // новый текст
  enabled,       // пользователь может отключить
  match: { status: "exact" | "by_text" | "not_found", p_indices, score },
  note           // комментарий разбора / Gemini
}
```

| action | Формулировка в документе | Что делает программа |
|---|---|---|
| `replace_clause` | «Пункт X изложить в следующей редакции: …»; строка протокола «было / стало» | Пословный diff старого и нового текста пункта, правки вносятся точечно |
| `insert` | «Дополнить пунктом X следующего содержания…»; «Отсутствует» в колонке «было» | Новый абзац с той же автонумерацией, что у соседа. `target` — номер нового пункта, `anchor` — после какого пункта вставить (необязательно; по умолчанию — после пункта X−1 со всеми подпунктами, для X.1 — сразу после пункта X, иначе — после предыдущей правки) |
| `delete_clause` | «Пункт X исключить»; «Исключить» в колонке «стало» | Весь пункт помечается удалённым |
| `replace_words` | «В пункте X слова «…» заменить словами «…»» | Замена только указанного фрагмента |
| `renumber` | «Пункты 5.4–5.6 считать пунктами 5.5–5.7» | Меняет текстовые номера. Для автонумерации ничего не делает, Word перенумерует сам |

Пункт может состоять из нескольких абзацев. При вставке или замене многоабзацного текста абзацы разделяются переводом строки в `new_text`.

## 5. Разбор источников

### 5.1. Протокол разногласий в .docx (локально, без сети)
- **Таблица.** Ищется таблица, в шапке которой есть слово «Редакция». Если такой нет, берётся первая таблица из 3–4 колонок. Первая колонка — номер пункта.
- **Применяемая редакция.**
  - Если есть колонка «Согласованная редакция» / «Итоговая редакция», берётся она.
  - Иначе берётся последняя колонка с редакцией (редакция стороны, предложившей изменения).
  - Пользователь может выбрать другую колонку. Тогда правки пересобираются.
- **«Было».** Колонка «было» — первая колонка с редакцией после колонки номера.
- **Служебные слова.** «Отсутствует» / «—» в «было» означают вставку. «Исключить» / «Исключён» / «—» в «стало» означают удаление.
- **Номер пункта.** Номер извлекается из колонки номера. Поддерживаются форматы:
  - «п. 5.3», «5.3», «Пункт 5.3.»;
  - формат вкладки 1 «7.2 (7.2, 7.3 в редакции Стороны-2)»: берётся первый номер;
  - «Заголовок «…»», «Вводная часть», «Без номера»: правка сопоставляется только по тексту.
- **Совместимость.** Формат, который выдаёт вкладка 1, разбирается без потерь (это проверяет round-trip-тест).

### 5.2. Скан (PDF, JPG, PNG) — через Gemini
- Файл отправляется в Gemini (`inline_data`). В одном запросе Gemini распознаёт текст и возвращает JSON по схеме правок, а также реквизиты источника: вид, номер, дату.
- Распознанный текст сохраняется в архив как `<имя>.распознано.txt`.
- Перед отправкой интерфейс показывает, какие файлы уйдут в Gemini.

### 5.3. Дополнительное соглашение в .docx
- **Есть ключ.** Текст ДС отправляется в Gemini, ответ приходит в той же JSON-схеме.
- **Нет ключа или нет сети.** Используется локальный разбор регулярными выражениями по типовым формулировкам:
  - «изложить в следующей редакции»;
  - «дополнить пунктом … следующего содержания»;
  - «исключить»;
  - «слова «…» заменить словами «…»»;
  - «считать пунктами».
  Правки, которые не удалось разобрать, показываются как «требует ручной правки».

### 5.4. Проверка перед сборкой
Все правки выводятся таблицей: источник, пункт, действие, было, стало, статус сопоставления. Пользователь может:
- включить или выключить правку;
- исправить номер пункта, действие и тексты;
- добавить правку вручную;
- переставить источники.

После изменения номера или текста правка сопоставляется с договором заново.

## 6. Сопоставление правки с договором

1. По номеру `target` ищется пункт в карте нумерации договора (раздел 7). Эта карта учитывает все уже применённые правки предыдущих источников.
2. Если `old_text` известен, он сравнивается с текстом найденного пункта (`difflib.SequenceMatcher`, без номера, с нормализацией пробелов и кавычек). При score ≥ 0,85 статус — `exact`.
3. Если номер не найден или текст не совпал, `old_text` ищется по всем пунктам договора. Лучшее совпадение со score ≥ 0,75 получает статус `by_text`, и номер подменяется фактическим.
4. Иначе ставится статус `not_found`. Правка подсвечивается красным и не применяется, пока пользователь её не исправит.

## 7. Автонумерация

Модуль `numbering.py` вычисляет номер каждого абзаца так, как его показывает Word.

- **Откуда берётся `numPr`.** Из самого абзаца (`w:pPr/w:numPr`) или из стиля абзаца с учётом цепочки `basedOn` в `styles.xml`.
- **Что учитывается в `numbering.xml`:**
  - `w:num` → `w:abstractNum` (в том числе `numStyleLink` / `styleLink`);
  - `w:lvlOverride` / `w:startOverride` и переопределение `w:lvl`;
  - у уровня: `w:start`, `w:numFmt`, `w:lvlText` (`%1.%2.`), `w:lvlRestart`, `w:isLgl`;
  - `numFmt`: decimal, decimalZero, lowerLetter, upperLetter, lowerRoman, upperRoman, russianLower, russianUpper, bullet, none.
- **Счётчики.** Счётчики ведутся по abstractNum. Переход на более высокий уровень сбрасывает нижние. `numId = 0` отключает нумерацию.
- **Удалённые абзацы.** Абзац, удалённый правкой (знак абзаца в `w:del` и весь текст удалён), в «принятом» виде не считается.
- **Текстовая нумерация.** Если у абзаца нет автонумерации, номер берётся из начала текста (`NUM_RE`), как сейчас.
- **Результат:** `[{p_index, number, level, auto: bool, text}]`.

### Применение правок к автонумерованным пунктам
- Новый пункт копирует `pPr` соседа (того же уровня), включая `numPr`. Номер в текст не пишется, его ставит Word.
- При удалении пункта знак абзаца помечается как удалённый. После принятия правок Word перенумерует остальные пункты сам.

### Применение правок к пунктам с текстовой нумерацией
- Номер пишется в текст нового пункта. Он берётся из `target` правки.
- Последующие номера автоматически не сдвигаются. Если источник явно перенумеровывает пункты, это делается правкой `renumber`. Иначе в отчёт попадает предупреждение.

### Перекрёстные ссылки
Программа ищет в тексте ссылки вида «п. 5.3», «пунктом 5.3 настоящего Договора». Если пункт, на который ссылаются, удалён или сменил номер, в отчёт попадает предупреждение. Автоматически ссылки не исправляются.

## 8. Редлайн (`redline.py`)

- Работа идёт с `word/document.xml` через ElementTree с сохранением пространств имён. Другие части пакета (styles, numbering, header и т. д.) копируются без изменений.
- **Пословный diff.** Текст пункта бьётся на токены (слова, пробелы, знаки препинания), и `difflib` сравнивает старую и новую последовательности.
  - Неизменённые токены остаются в исходных run'ах.
  - Удалённые токены переносятся в `w:del` с `w:delText`; форматирование (`rPr`) сохраняется.
  - Вставленные токены оборачиваются в `w:ins`; `rPr` берётся у соседнего run'а.
  - Run'ы, если нужно, разрезаются по границам токенов.
- **Многоабзацный пункт.** Абзацы сопоставляются через diff по абзацам.
  - Лишние абзацы удаляются: текст и знак абзаца помечаются `w:del`.
  - Недостающие абзацы вставляются: новый `w:p` с `pPr` соседа и знаком абзаца в `w:ins`.
- **Атрибуты правок.** У каждого `w:ins` / `w:del` есть уникальный `w:id`, `w:author` = автор источника и `w:date` = время сборки (ISO 8601).
- **Последовательное применение.** Источники применяются по порядку. После каждого источника карта нумерации и тексты пересчитываются на «принятом» виде.
  - Если правка удаляет текст, вставленный предыдущим источником, `w:del` вкладывается в существующий `w:ins`.
  - Если правка меняет текст, вставленный предыдущим источником, применяются те же правила.
- **Договор уже содержит правки.** Программа предупреждает пользователя. Базой считается принятый вид, существующие правки остаются в документе как есть.
- **Результат валиден.** Документ открывается в Word без ошибок восстановления.

## 9. История и архив (`history.py`)

- **Папка прогона.** Каждый прогон любой вкладки создаёт папку `Архив/ГГГГ-ММ-ДД_ЧЧММСС_<имя договора>/`:
  - `вход/` — копии всех входных файлов под исходными именами;
  - `результат/` — итоговая редакция или протокол разногласий; для сканов здесь же лежит `*.распознано.txt`;
  - `отчёт.md` — отчёт о сборке (для вкладки 2);
  - `meta.json`:
    ```
    { id, created, kind: "protocol" | "final", contract, inputs: [...], outputs: [...],
      sources: [{label, kind, file, edits_total, edits_applied}], warnings }
    ```
- **Список истории.** Вкладка «История» собирается сканированием `Архив/*/meta.json`, отдельного индекса нет, поэтому его нельзя рассинхронизировать. Новые прогоны показываются сверху. Есть поиск по имени договора и фильтр по типу.
- **Кнопки.**
  - «Открыть папку» выполняет `open -R <папка>`, Finder подсвечивает папку прогона.
  - «Открыть результат» выполняет `open <файл>`, файл открывается в Word.
  - Путь для открытия определяется на сервере по `id` прогона. Сервер проверяет, что путь лежит внутри `Архив/`. Произвольные пути с клиента не принимаются.
- **Хранение.** Удалять прогоны из программы нельзя. Пользователь удаляет папки в Finder сам.
- **Git.** `Архив/` добавлен в `.gitignore`.

## 10. Gemini (`gemini.py`)

- **Транспорт.** Только стандартная библиотека: `urllib.request` → `https://generativelanguage.googleapis.com/v1beta/models/<model>:generateContent`.
- **Ключ.** Ключ передаётся в заголовке `x-goog-api-key`, а не в URL.
- **Формат ответа.** Используются `generationConfig.responseMimeType = "application/json"` и `responseSchema` (схема правок + реквизиты источника + распознанный текст).
- **Настройки.** Ключ и модель читаются из `.env` (`GEMINI_API_KEY`, `GEMINI_MODEL`). Модель по умолчанию — `gemini-3.8-flash` (стабильная Flash на октябрь 2026).
  - В окне настроек ключ можно задать или заменить. Ключ сохраняется в `.env` с правами `600`.
  - Значение ключа в интерфейс не возвращается, показывается только «задан / не задан».
- **Ограничения запроса.** Тайм-аут 120 с, файл до 20 МБ (`inline_data`).
- **Ошибки показываются понятным текстом:** нет ключа, неверный ключ, превышена квота, нет сети.
- **Промпт:**
  - роль — юрист, разбирающий изменения к договору;
  - требовать дословные цитаты нового текста без пересказа;
  - номера пунктов указывать так, как они записаны в документе;
  - нераспознанное помечать в `note`.
- **Логи и архив.** Ключ не пишется в логи и в архив.

## 11. Интерфейс

- **Вкладки:** «Протокол разногласий» (существующая) | «Итоговая редакция» | «История». Справа кнопка ⚙ «Настройки» (ключ Gemini, модель).
- **Вкладка «Итоговая редакция»:**
  1. Зона загрузки договора (.docx). После загрузки видны имя договора, число пунктов, вид нумерации (авто / текст / смешанная) и предупреждение, если в договоре уже есть правки.
  2. Зона загрузки источников (несколько файлов: .docx, .pdf, .jpg, .png). По каждому файлу видны вид, автор, дата и порядок (стрелки ↑↓). Отметка «☁ Gemini» означает, что файл будет отправлен в Gemini.
  3. Таблица правок (раздел 5.4) с цветными статусами: зелёный — `exact`, жёлтый — `by_text`, красный — `not_found`.
  4. Нижняя панель: «Собрать итоговую редакцию» и счётчик применяемых правок. Результат скачивается и одновременно сохраняется в архив, после чего появляется кнопка «Показать в Finder».
- **Вкладка «Протокол разногласий»** работает как раньше. Дополнительно каждый созданный протокол сохраняется в архив.

## 12. Нефункциональные требования

- Только стандартная библиотека Python 3.9+, никакого pip.
- Сервер слушает только 127.0.0.1.
- Данные уходят в сеть только при явной обработке источника через Gemini.
- `Протокол разногласий.html` не меняется: новые функции есть только в Python-версии.
- Тесты: `python3 -m unittest discover tests`.

## 13. Критерии приёмки

1. **Round-trip.**
   - Исходник получается из `Договор_товарищество_обезличенный.docx` отклонением всех правок.
   - Протокол строится вкладкой 1 из файла с правками.
   - Вкладка 2 применяет протокол к исходнику.
   - Принятый вид результата совпадает с принятым видом файла с правками (по абзацам, с нормализацией пробелов).
2. **Автонумерация.** На синтетическом договоре со списками вставка пункта между 5.2 и 5.3 и удаление 4.1 дают корректную нумерацию после принятия правок.
3. **Несколько источников.** ДС № 1 и ДС № 2 применяются последовательно. ДС № 2 ссылается на номер, появившийся после ДС № 1. В Word видно два автора правок.
4. **Скан.** Скан протокола разбирается через Gemini, правки попадают в таблицу проверки.
5. **История.** Каждый прогон обеих вкладок появляется в истории. «Открыть папку» открывает Finder на нужной папке.
6. **Валидность.** Результат открывается в Word без сообщения о повреждении.
